# 好友聊天樂觀送出設計

## 目標

使用者送出好友私訊後，不等待 REST 請求完成就立即在目前對話顯示本人訊息，降低網路延遲造成的等待感。

## 現況

`chatStore.sendMessage()` 目前會先等待 `sendDirectMessageApi()` 成功，再把伺服器回傳的正式訊息加入對話。`FriendChatPanel` 也只在成功後清空輸入框，因此請求期間畫面沒有新訊息回饋。

## 資料與狀態設計

- 樂觀訊息由 `chatStore` 管理，與正式訊息共用既有 `conversations`，避免元件維護第二份訊息列表。
- 每次送出建立一筆只存在前端的暫存訊息，包含臨時負整數 ID、目前玩家 ID、好友 ID、正規化內容、目前時間及樂觀訊息標記。
- 既有訊息驗證與合併流程只額外接受帶明確標記的臨時負整數 ID；未標記或形狀不合法的訊息仍被拒絕。
- 目前 `isSending` 會阻止並行送出，因此同一時間最多只有一筆待確認訊息；臨時 ID 仍由模組內遞減計數器產生，避免同一生命週期內重複。

## 送出流程

1. `sendMessage()` 完成好友 ID、內容與登入玩家驗證。
2. Store 建立暫存訊息並立即合併至該好友的對話，畫面及自動捲動會沿用既有 reactive 流程更新。
3. Store 呼叫既有聊天 REST API。
4. 成功取得正式 `directMessage` 時，移除暫存訊息並加入正式訊息，由正式 ID 與時間參與既有去重排序。
5. 若 API 拒絕、丟出錯誤或沒有回傳有效正式訊息，移除暫存訊息並設定既有「訊息送出失敗」錯誤訊息。

## 輸入框行為

- `FriendChatPanel.submitMessage()` 在呼叫 Store 前保存原始輸入內容，呼叫後立即清空輸入框。
- Store 成功回傳正式訊息時維持空白。
- Store 回傳 `null` 時，將原始輸入內容還原，方便使用者再次嘗試。
- 送出期間沿用 `isSending` 停用輸入框與按鈕，因此失敗還原不會覆蓋新的使用者輸入。

## 錯誤與一致性

- 失敗的暫存訊息不保留，不新增失敗標記或重送按鈕。
- 不修改 REST、Socket.IO 或資料庫契約。
- 伺服器正式訊息仍是最終資料來源；暫存資料不寫入 localStorage。
- 若正式訊息也經其他既有載入流程進入對話，既有正式 ID 去重規則維持不變。

## 驗證

- Store 測試使用可控制的未完成 API Promise，驗證請求完成前暫存訊息已出現在對話。
- 成功測試驗證暫存 ID 被正式訊息取代，內容不重複且 `isSending` 復原。
- 失敗測試驗證暫存訊息被移除、錯誤訊息被設定且 Store 回傳 `null`。
- 元件測試驗證送出後立即清空輸入框，失敗時還原原始文字。
- 執行好友聊天相關測試與 `npm run build`。

## 非目標

- 不支援同時送出多則訊息、離線佇列、重送按鈕或永久失敗狀態。
- 不新增後端 `clientMessageId` 或冪等性契約。
- 不修改訊息泡泡配色、版面或聊天通知功能。
